# Current Ruhi architecture and evaluation boundary

Inspected before NLP/model repairs. The previous v5.2 working changes remain in place.

Input goes through `runSemanticAssistant` in `liveAssistant.ts`. It synchronizes native scene objects, loads the existing four-head TensorFlow.js model through `hierarchicalModel.ts`, parses bounded structured commands in `semanticParser.ts` and compatibility language modules, and uses `SemanticEngine` / `ConversationEngine` / `FollowUpEngine` for references, persistent pending questions, corrections and planning. `executionPlanner.ts` invokes real geometry or the mathematical kernel. `resultVerifier.ts` checks planned effects and native committed objects. `workspaceBridge.ts` commits to the registered graph workspace, whose rows/vertices are read back. The assistant generates controlled responses from actual results.

The classifier produces action, subAction, mode and objectType scores. It does not itself compute geometry or supply scene memory. The normal entry point already favors validated deterministic plans, using neural fallback for selected unhandled creations. Therefore a classifier accuracy improvement is not automatically an end-to-end improvement.

The 2D graph UI is `MathLabGraphingCalculator.tsx`, geometry adaptation/construction is in `geometryAdapter.ts`, the graph studio and construction engine, and independent mathematical algorithms are in `src/math-robo/kernel`. Native object IDs/labels, selections, scene snapshots, dependency definitions and undo/redo are owned by the bridge and semantic engine. Existing style fields initially expose only a common color; a distinct fill/stroke capability must be implemented and rendered before tests can credit it. Angle modification, selective color undo and extension should not be inferred from registry names alone.

The existing Training Lab is `SemanticTrainingLab.tsx`, with worker training and candidate evaluation/export. `buildPolicy.ts` and `build-ruhi.mjs` strip training UI from the student production build. This is distribution separation, not authentication. Local developer filesystem access authorizes CLI training; scripts write separate candidate files and cannot publish shared production weights. An admin build must be served behind host/storage access controls. Public browser booleans do not protect a shared deployment boundary.

Tests use real browser graph state through the same inference/execution entry point as the assistant. Scene initialization uses natural-language fixture requests, never expected actions. Dataset contracts live exclusively in test modules. Baseline harness attempt one used incomplete label syntax; its 149 setup blocks are retained separately and the corrected harness reruns baseline before changing application sources or training. No application/model change occurred between these attempts.

The immutable source has 300 records in 237 scenarios. Normalized v1 retains original fields and IDs. Seeded scenario partition: 210 development, 47 validation, 43 held-out; related turns stay together. Repeated templates cross splits, so this pilot split alone cannot prove paraphrase generalization. All-300 results are explicitly regression, including the required baseline observation. Only development failures may guide repairs; validation selects checkpoints, and held-out does not enter training.
